## Stack

## Users

**【推断·待确认】** 唯一真实用户 = 开发者本人：有训练习惯、会 React、想用数据化方式管理自己的训练/饮食/补剂；场景为健身房与家庭训练；不做面向公众的分发（个人主体小程序，体验版自用）。

## Product Purpose

一个「会自己复盘进化」的私人健身中枢：把训练计划、每次记录、饮食、补剂放在一起，用 LLM 把周期数据变成下一周期的决策和教练式建议。成功标准：**【推断·待确认】** 用户本人愿意每天真实使用、能坚持跟完一个个训练周期、不再需要同时开 Keep + 薄荷 + 备忘录三个 app。

## Positioning

竞品验证后的空白组合：①**周期复盘 → 下周期动作与重量自动决策**（Fitbod 只有逐次自适应，Hevy/Strong 只有静态模板）；②**知识库上传，让 LLM 把外部资料消化进自己的计划**（无先例）；③**体检报告 + 训练数据 → 个性化补剂推荐**（商业玩家 Care/of、Rootine 均死于卖货模式，纯软件建议无人提供）。个人自用免订阅，护城河是「比商业产品更懂我一个人」。

## Operating Context

- 训练日：打开小程序 → 开始训练 → 逐组记录（重量/次数/RPE）→ 休息计时 → 结束。
- 周期结束（如三分化 3 练 1 休跑完）：查看周期总结 → 确认/微调下周期计划。
- 每餐：拍照 → AI 初估 → 修正确认。
- 每日：补剂清单打卡（剂量+时机来自推荐引擎）。
- **【推断·待确认】** 单人使用，数据一致性/并发不是问题；换设备偶发。

## Capabilities and Constraints

**已确认能力（用户 brief）**：
1. 训练模式：分化训练（二/三/四/五分化）、力量训练（卧推计划）、减脂计划（有氧等）。
2. 计划流程：设目标（时间/体重/各动作重量）→ 每次训练记录 → 周期结束总结 → 决定下周期动作与重量。
3. 云端知识库：文字/txt 上传（两种 LLM 模式：总结优化现有计划 / 新增计划），可下载。
4. 饮食：拍照自动算卡路里 + 合理性分析。
5. 补剂管理：营养师知识库；体检报告 + 训练计划 + 主观感受 → LLM 推荐每日补剂/剂量/时机。
6. 训练模块有 LLM 能力。
7. **明确不做**（现阶段）：视频动作纠正。

**约束**：
- 个人主体小程序：不能用微信支付、web-view；以体验版分发自用，不走审核发布。
- LLM 调用必须经服务端转发（域名白名单）；输出需 JSON Schema 校验。
- 补剂/体检相关输出必须附「非医疗建议」免责声明。
- 敏感健康数据：**体检报告不上云，仅存设备本地（2026-09-12 已拍板）**；LLM 解析走「阅后即焚」云函数（服务端不落库不留日志）或手动录入指标。

## Product Principles

1. **周期高于单次**：产品以「周期」为一等公民，每次记录都是周期复盘的输入。
2. **AI 建议，用户拍板**：LLM 出草案（下周期/补剂/热量），规则引擎给依据，人一键确认——不做黑箱自动改计划。
3. **修正要便宜**：所有 AI 识别结果（卡路里/计划解析）一触可改，改过的沉淀为个人资产（常用食物库/动作库）。
4. **数据可带走**：全量导出/导入是原则而非功能。
5. **诚实对待误差**：拍照估卡路里承认 ±30% 误差，趋势重于单餐。
